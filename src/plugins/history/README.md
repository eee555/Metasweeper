# 历史记录插件

自动记录每一局扫雷数据（SQLite 持久化），并提供查询、过滤、排序、计算列、录像播放与导出功能。

每局游戏结束（无论胜负）都会自动写入本地数据库，无需任何手动操作。

## 快速上手

在插件管理器中启用本插件后，主界面会出现「历史记录」标签页：

1. 点击 **查询** —— 显示全部历史记录（默认每页 50 条）；
2. 在表格上 **右键** 一条记录 —— 可以播放、导出、复制或删除；
3. 用 **过滤** / **排序** / **列设置** / **计算列** 按钮按需定制视图。

## 界面功能

### 查询与分页

- **查询**：按当前过滤、排序条件重新查询；
- 底部分页栏：**上一页 / 下一页**、页码跳转、每页条数（10 ~ 1000，可在插件设置中改默认值）；
- 分页栏右侧显示总行数与总页数。

### 过滤

点击 **过滤** 打开条件编辑器，支持多行条件组合：

- 每行：`括号` + `字段` + `比较符` + `值` + `逻辑连接`；
- 比较符支持：等于、不等于、大于/小于（含等于）、包含 / 不包含；
- 多行之间可用 **与 / 或** 连接，并支持左右括号分组；
- 时间字段（开始时间、结束时间）可以直接填 `2024-01-01 12:00` 这样的可读格式；
- 逻辑错误（如括号不匹配）会弹窗提示，不会执行错误查询。

示例：`开始时间 > 2024-01-01` 且 `游戏状态 = 胜利` 且 `用时 < 60`。

> 关闭软件时会记住当前的过滤与排序条件，下次打开自动恢复。

### 排序

点击 **排序** 打开排序编辑器：

- 可按任意字段（含计算列）升序 / 降序排列；
- 支持多级排序（先按难度，再按用时，以此类推）。

### 列设置

点击 **列设置** 选择表格显示哪些列，支持上下移动调整顺序。

### 计算列

点击 **计算列** 可以在表格中新增"派生列"，本质是 SQL 表达式：

- 表格中有 **列名 / SQL 表达式 / 结果类型** 三项，点 **添加** 新建一行；
- 表达式里可以引用任何物理字段，例如 `py_safe_div(bbbv_solved, rtime)` 即 3BV/s；
- 点 **验证** 会检查所有表达式是否合法；
- 还可以在下方编辑区写 **自定义 Python 函数**（须以 `py_` 开头），供 SQL 表达式调用。

内置的默认自定义函数：

| 函数 | 作用 |
|------|------|
| `py_safe_div(a, b)` | 安全除法，除零或空值返回 0 |
| `py_safe_mod(a, b)` | 安全取模，除零或空值返回 0 |
| `py_days_since(ts)` | 微秒时间戳距今天数（今天 = 0） |
| `py_months_since(ts)` | 微秒时间戳距今月数（当月 = 0） |

默认已预置若干计算列（3BV/s、IOE、THRP、CORR、距今天数等），可自由删改。

### 右键菜单

在表格记录上右键：

| 操作 | 说明 |
|------|------|
| **播放** | 用元扫雷主程序打开该局录像回放 |
| **导出录像** | 另存为 `.evf` 文件 |
| **复制 JSON** | 把该行所有可见字段复制为 JSON 到剪贴板 |
| **删除** | 删除该条记录（含录像数据），有确认弹窗，**不可恢复** |
| **刷新** | 重新加载数据 |

## 插件设置

在插件管理器中打开本插件的设置页：

| 设置项 | 默认 | 说明 |
|--------|------|------|
| 小数位数 | 2 | 表格中浮点数显示的小数位数 |
| 每页条数 | 50 | 打开页面时默认的每页记录数 |
| 录像最低 3BV 完成率（%） | 30 | 清理低于该完成率的录像字节，保留历史统计；设为 0 可保留全部录像 |

计算列、过滤、排序、列显示状态都会自动保存，无需手动备份。

## 数据存储

数据库与配置都位于插件数据目录：

```
<数据目录>/plugin_data/HistoryPlugin/
├── history.db                  # SQLite 数据库（元数据 + 录像数据）
└── history_show_fields.json    # 列显示配置
```

- 新录像的元数据、逐条 zlib 压缩的录像暂存数据及索引在同一事务中落盘；新记录不再双写旧 `replay_data` 表。暂存不足一块也可以立即播放和导出，退出后仍会保留。
- `history.board` 保存每格一个字符的 ASCII 完成局面：`*` 表示雷，`0`~`8` 表示数字；行列由 `row` / `column` 字段给出。表格显示实际字符串，过滤可直接用「包含子串」，悬浮预览直接查库中的 row/column/board 后切分显示。旧 JSON / 雷图 BLOB 会后台迁移为 ASCII。
- 后台线程把最多 128 条录像编码为列式 LZMA 分块，压缩和逐字节还原校验在写事务外完成；通过校验后才用短事务替换暂存数据。保存、删除和后台提交由同一数据库写线程处理，排队时优先处理正常保存。删除记录只写短事务墓碑并立即唤醒后台：后台重组仅含死槽位的分块、把墓碑索引从块中摘除，成功后请求一次空闲页回收；删除路径不等待 LZMA 重编码。启动与低完成率清理后也会检查残留墓碑块。
- 已有旧格式记录会分批迁移，校验通过并确认输入未被并发修改后才清理对应旧副本；低完成率录像清理也会显示处理进度。迁移批次与各分块的解压、编码和压缩在有界准备线程池中并行完成（默认 2 个线程，在途任务数受内存限制），但仍由同一个数据库写线程按序提交短事务，正常保存优先。冲突或失败的计划不提交、不计数，源数据保留到下次启动继续处理。无维护任务、完成、失败或关闭插件后进度条隐藏。
- 并行收益有限，原因是耗时集中在纯 Python 代码上。早期热态实测 1024 条（每条约 1000 事件）：串行 2.11s、2 线程 1.58s、4 线程 1.67s；单个批次内 `encode_group` 占 36%、`decode_group` 占 42%、`split_evf` 占 10%，这三段都在持有 GIL 时运行，只有 `lzma`（9%）、`zlib`（3%）和 `sha256` 会释放 GIL。
- 因此优化方向是减少 GIL 内的字节搬运，而不是提高并行度。`replay_codec` 已改为：事件尺寸用查表代替逐次分支判断，字节流用 `bytearray.extend`/切片搬运代替逐字节 `append`，长度表用一次 `struct.unpack` 解出。单批编解码从约 340ms 降到约 100ms。此后并行才真正生效：同负载下 2 线程约 1.3x、4 线程约 1.9x、6 线程约 1.95x，默认并行度因此设为 4（上限受 CPU 核数约束，低核机器退化为 2）。
- 进程池没有帮助：准备结果（解压后录像与编码块）需要跨进程序列化，且 `sqlite3.Connection` 不能共享，实测比串行更慢。若将来要进一步提速，可考虑把 `_scan_events`/`encode_group` 移植到 C 扩展或用 `numpy` 做向量化，而不是继续加线程。
- 每次插件启动完成首轮积压压缩后，尝试执行一次 `VACUUM` 回收此前删除留下的空闲页；没有空闲页时只做一次轻量检查。回收请求排在后台维护队列，正常保存优先；回收失败时下次启动再尝试。
- 数据库使用 WAL 支持查询与写入并行。换电脑或手动备份时先正常退出程序，再拷贝 `HistoryPlugin` 整个文件夹；程序运行时不要只复制 `history.db`，因为尚未归并的数据可能位于 `history.db-wal`。

## 字段速查

| 字段 | 含义 | 字段 | 含义 |
|------|------|------|------|
| `replay_id` | 记录编号 | `game_state` | 结局状态（胜利/失败/重开等） |
| `nf` | 是否 NF（无标旗） | `row` / `column` / `mine_num` | 盘面行、列、雷数 |
| `rtime` | 用时（秒） | `left` / `right` / `double` | 左键、右键、双击次数 |
| `level` | 难度（3 初级 / 4 中级 / 5 高级 / 6 自定义） | `cl` / `ce` | 点击次数、有效点击数 |
| `bbbv` / `bbbv_solved` | 3BV 总数、已解决数 | `zini` | ZINI |
| `flag` | 标旗数 | `path` | 鼠标路径长度 |
| `start_time` / `end_time` | 开始 / 结束时间 | `mode` | 游戏模式（标准、无猜等） |
| `op` / `isl` / `pluck` | OP 区间数、ISL 区间数、Pluck | `is_official` / `is_fair` | 是否正式 / 公平局 |

## 常见问题

**Q：看不到最近一局的记录？**
点击右键菜单的 **刷新** 或顶部 **查询** 按钮即可（插件正常情况下会自动刷新）。

**Q：表格很卡 / 记录太多？**
用 **过滤** 缩小范围，或在设置里把每页条数调小；也可以把不需要看的列隐藏掉。

**Q：计算列写错了，能恢复默认吗？**
删除所有自定义列后，重新启动插件即可恢复默认的计算列配置。

**Q：误删了记录怎么办？**
删除不可恢复。建议定期备份 `history.db` 文件。

**Q：其他插件能读我的历史记录吗？**
可以。本插件注册了只读的 `HistoryService` 服务，其他插件（如统计插件）可通过服务接口查询记录，但不能修改或删除数据。
